## 1. Итоговая оценка

Проект в текущем виде **не рекомендуется устанавливать на production-сервер или хост с ценными данными**.

В проверенном снимке не обнаружено явных признаков намеренного вредоносного кода: майнера, reverse shell, скрытой отправки proxy secrets, встроенного SSH-ключа автора или обфусцированной полезной нагрузки. Тем не менее проект содержит небезопасные настройки, ошибки firewall и неконтролируемую цепочку поставок с выполнением загруженного из Интернета кода от `root`.

Главные блокирующие проблемы:

1. Публичный управляющий API Telemt без аутентификации.
2. Загрузка и выполнение изменяемых веток `main` и последних релизов без проверки хэшей или подписей.
3. Watchtower с доступом к Docker socket.
4. Глобальное открытие SSH в начале цепочки `INPUT`.
5. Ошибки и обходы SYN limiter в вариантах iptables/nftables.
6. Неполное удаление root-служб и firewall-артефактов.

## 2. Область и ограничения аудита

Репозиторий является не форком исходного кода официального Telegram MTProxy, а shell-менеджером и набором установщиков. Фактическая обработка MTProto-трафика передаётся динамически загружаемым проектам Telemt, MTG, mtproto.zig, MTProxyL и другим компонентам.

Исполняемый код проверенного `HEAD` соответствует релизу `v1.98`; изменения после тега затрагивают только README. Теги проекта являются lightweight-тегами, поэтому отдельной криптографически подписанной сборки релиза нет.

Аудит имеет следующие ограничения:

- установщики и сетевые службы не запускались, чтобы не изменять хост;
- загружаемые бинарники и их build pipelines не подвергались полному аудиту;
- выводы относятся только к указанному commit;
- содержимое внешних веток `main`, образов и последних релизов может измениться без изменения этого репозитория;
- отсутствие найденного бэкдора не является доказательством отсутствия всех возможных уязвимостей.

## 4. Подробные находки

### SA-01. Публичный управляющий API Telemt без аутентификации

**Уровень:** высокий  
**Файл:** [`proxys/telemt_in_docker1.sh`](proxys/telemt_in_docker1.sh#L203-L254)

Docker-установщик создаёт следующую конфигурацию:

```toml
[server.api]
enabled = true
listen = "0.0.0.0:9091"
whitelist = ["0.0.0.0/0"]
```

Порт дополнительно публикуется как:

```yaml
- "9091:9091"
```

`auth_header` и `read_only` не задаются. Минимально подтверждённое воздействие:

- `GET /v1/users` возвращает готовые `tg://proxy`-ссылки с proxy secret;
- API статистики может раскрывать IP подключённых клиентов;
- посторонний пользователь получает возможность использовать прокси;
- доступны изменяющие API-методы, хотя постоянная запись конфигурации может завершаться ошибкой из-за монтирования `config.toml` как `:ro`.

Получение proxy secret само по себе не позволяет расшифровать Telegram-переписку и не означает выход из контейнера.

**Рекомендации:**

- отключить API, если он не требуется;
- иначе слушать только `127.0.0.1:9091`;
- публиковать Docker-порт как `127.0.0.1:9091:9091`;
- установить случайный `auth_header`;
- включить `read_only = true`;
- ограничить whitelist локальным адресом или административной сетью;
- закрыть `9091/tcp` в cloud firewall/security group.

### SA-02. Невоспроизводимая root-цепочка поставок

**Уровень:** высокий  
**Файлы:** [`install_main.sh`](install_main.sh#L4-L112), [`install.sh`](install.sh#L542-L884), [`main.sh`](main.sh#L1018-L1304)

Проект загружает из Интернета и немедленно выполняет от `root`:

- собственные файлы и манифест из изменяемой ветки `main`;
- установщик Telemt из `main`;
- установщик mtproto.zig из `main`;
- MTProxyL, 3x-ui, Remnawave, censorcheck и панели;
- последний MTG release;
- Zapret2 без проверки контрольной суммы.

Загрузки не закреплены на commit SHA или image digest и не проверяются по независимому SHA-256 либо криптографической подписи. Компрометация любого upstream-репозитория, GitHub-аккаунта или release pipeline даст выполнение кода от `root` при следующей установке или обновлении.

Это архитектурный риск, а не доказательство того, что текущий upstream уже скомпрометирован.

**Рекомендации:**

- отказаться от `curl .../main | sudo bash`;
- закрепить каждый источник на проверенный commit SHA;
- закрепить контейнеры на image digest;
- хранить проверенные SHA-256 отдельно от загружаемого файла;
- по возможности vendor-ить проверенные скрипты в репозиторий;
- отключить автоматическое root-обновление;
- устанавливать файлы атомарно после успешной проверки подписи или хэша.

### SA-03. Watchtower имеет root-эквивалентный доступ к Docker

**Уровень:** высокий  
**Файл:** [`proxys/telemt_in_docker1.sh`](proxys/telemt_in_docker1.sh#L245-L254)

Создаётся контейнер из неприкреплённого образа `containrrr/watchtower`, которому передаётся:

```yaml
- /var/run/docker.sock:/var/run/docker.sock
```

Контроль Docker daemon позволяет создавать привилегированные контейнеры и монтировать файловую систему хоста. Поэтому компрометация или вредоносное обновление такого образа эквивалентны компрометации хоста.

**Рекомендация:** удалить Watchtower и выполнять контролируемые обновления только после проверки конкретного digest.

### SA-04. nftables classic limiter работает в обратную сторону

**Уровень:** высокий для доступности  
**Файл:** [`data/rules.sh`](data/rules.sh#L520-L540)

Генерируется правило:

```nft
limit rate 1/second burst 1 packets ... drop
```

В nftables выражение `limit rate` без `over` совпадает с пакетами в пределах установленной скорости. В результате первые легитимные SYN отбрасываются, а после исчерпания bucket правило перестаёт совпадать и последующий поток проходит дальше.

**Рекомендация:** для отбрасывания превышения использовать корректную семантику `limit rate over ... drop` и проверить итоговый ruleset интеграционными тестами.

### SA-05. Панель Telemt публикуется по HTTP

**Уровень:** высокий при выборе установки панели  
**Файл:** [`proxys/telemt_panel_amirotin.sh`](proxys/telemt_panel_amirotin.sh#L272-L341)

Обвязка загружает изменяемый upstream installer. Текущий upstream слушает `0.0.0.0:8080` и формирует публичный URL с `http://`.

При отсутствии отдельного TLS reverse proxy пароль и административная сессия могут быть перехвачены атакующим в сетевом пути.

**Рекомендации:** слушать только loopback/VPN-интерфейс, использовать HTTPS reverse proxy или SSH tunnel и не открывать порт панели в Интернет.

### SA-06. Глобальное разрешение SSH

**Уровень:** средний; высокий при слабой SSH-аутентификации  
**Файл:** [`data/rules.sh`](data/rules.sh#L136-L200)

Скрипт вставляет в начало `INPUT`:

```bash
iptables -I INPUT 1 -p tcp --dport "$SSH_PORT" -j ACCEPT
```

Это правило разрешает доступ к `sshd` с любого адреса и располагается раньше UFW, Fail2Ban, geo/source allowlist и других правил. Оно не удаляется функцией `remove_syn_fix`.

Само правило не обходит пароль или SSH-ключ, но расширяет поверхность атаки и отменяет ранее настроенное сетевое ограничение.

**Рекомендация:** не добавлять глобальный `ACCEPT`; сохранять существующую политику либо явно запрашивать административную CIDR-сеть.

### SA-07. Подделываемый «iOS fingerprint» обходит limiter

**Уровень:** средний  
**Файл:** [`data/rules.sh`](data/rules.sh#L157-L236)

Безлимитный `ACCEPT` выдаётся по TTL, длине пакета, TCP options и U32-паттернам. Эти поля контролируются сетевым стеком отправителя и могут быть воспроизведены через raw sockets/Scapy.

Удалённый атакующий может сформировать подходящий SYN и попасть в ранний безлимитный `ACCEPT`, обойдя hashlimit/reject. Следовательно, fingerprint нельзя использовать как security boundary или надёжную DDoS-защиту.

### SA-08. IPv6 и несколько портов защищаются неполно

**Уровень:** средний  
**Файлы:** [`data/rules.sh`](data/rules.sh#L527-L540), [`data/zapret2_fix.sh`](data/zapret2_fix.sh#L529-L688)

- iptables-варианты работают только с IPv4;
- Zapret2 создаёт таблицу семейства `ip`, а не `inet`;
- nft meter использует `ip saddr`;
- при нескольких портах первая итерация `sed` заменяет все `PORT_HERE`, поэтому последующие порты не получают собственных правил.

В результате публичный IPv6 или дополнительные proxy-порты могут обходить заявленное ограничение.

### SA-09. «Полное удаление» оставляет root-службу

**Уровень:** средний  
**Файлы:** [`main.sh`](main.sh#L454-L493), [`data/zapret2_fix.sh`](data/zapret2_fix.sh#L699-L717)

Удаление проекта не останавливает и не удаляет полностью:

- `mtpr-zapret2.service`;
- `/opt/zapret2`;
- `/etc/zapret2`;
- `/usr/local/sbin/mtpr-zapret2-start.sh`;
- часть nftables/iptables-конфигурации.

Root-служба может продолжать запускать загруженный бинарник после сообщения о полном удалении. Отдельная функция удаления Zapret2 также оставляет часть helper/watcher-файлов.

### SA-10. Отключена строгая проверка SSH host key

**Уровень:** средний  
**Файлы:** [`remote_ctl/telemt1_node.sh`](remote_ctl/telemt1_node.sh#L16-L19), [`remote_ctl/rules1_node.sh`](remote_ctl/rules1_node.sh#L16-L19)

Обе функции используют:

```text
StrictHostKeyChecking=no
```

При активной подмене DNS/BGP/ARP, повторном использовании IP или первой непроверенной ноде атакующий может имитировать удалённый сервер, перехватывать вводимые пароли и подменять ответы управляющих команд.

**Рекомендация:** использовать `StrictHostKeyChecking=yes` с заранее проверенным fingerprint или минимум `accept-new`, запрещающий изменившийся ключ.

### SA-11. Слабая защита MTG и proxy secret

**Уровень:** средний  
**Файл:** [`proxys/mtgv2_1.sh`](proxys/mtgv2_1.sh#L124-L161)

- скачивается последний MTG release без checksum/signature;
- `/etc/mtg.toml` создаётся без явного `umask 077` или `chmod 600`;
- при стандартном root umask конфиг с proxy secret, вероятно, будет доступен локальным пользователям;
- systemd unit не задаёт `User=` и запускает сетевой сервис от `root`;
- отсутствуют `NoNewPrivileges`, `ProtectSystem`, `ProtectHome`, `PrivateTmp` и ограничение capabilities.

Запуск от `root` сам по себе не является доказанной RCE, но значительно увеличивает последствия потенциальной уязвимости MTG.

### SA-12. Proxy checker может создавать ложное чувство безопасности

**Уровень:** средний  
**Файл:** [`proxy_checker.py`](proxy_checker.py#L59-L126)

Вызов `openssl s_client` не требует успешной проверки hostname и цепочки сертификата. Соединение с самоподписанным или неподходящим сертификатом может быть принято как успешное.

Дополнительно в ветке одиночного IPv4 без PQ используется необъявленная переменная `detail_pq`, что способно привести к `NameError`.

Checker также ориентирован на IPv4 и скрывает часть неуспешных endpoint, поэтому его результат нельзя считать доказательством безопасности TLS/PQ-конфигурации.

### SA-13. Предсказуемые временные файлы

**Уровень:** средний; потенциально высокий на shared-хосте  
**Файлы:** [`install_main.sh`](install_main.sh#L4-L40), [`main.sh`](main.sh#L1019-L1028), [`data/zapret2_fix.sh`](data/zapret2_fix.sh#L294-L317)

Используются фиксированные или предсказуемые пути в `/tmp`, после чего файлы читаются, перемещаются или выполняются от `root`.

На системе без `fs.protected_symlinks`, `fs.protected_regular` и аналогичных защит локальный пользователь может подготовить symlink или принадлежащий ему файл, организовать TOCTOU-подмену и добиться повреждения root-файла либо выполнения изменённого скрипта/архива.

**Рекомендация:** использовать `mktemp -d`, безопасные права, `trap` для очистки и атомарную установку после проверки хэша.

### SA-14. Перезапись системной конфигурации без резервной копии

**Уровень:** средний  
**Файл:** [`main.sh`](main.sh#L421-L446)

Скрипт способен перезаписать:

- `/etc/systemd/system/telemt.service.d/limits.conf`;
- `/etc/sysctl.d/99-custom.conf`.

Это может удалить ранее заданные `User=`, `NoNewPrivileges=`, `ProtectSystem=` и другие защитные директивы. Uninstall не восстанавливает прежнее содержимое.

## 5. Дополнительные замечания

- Proxy secret и полная ссылка печатаются в терминал и могут попасть в shell history, CI-логи или снимки экрана.
- Некоторые IP lookup выполняются без явного `https://`; MITM может подменить публикуемый адрес прокси.
- U32/MARK-правило добавляется без проверки существования и может дублироваться после перезапусков.
- Используется общий firewall mark `0x400`, который может конфликтовать с VPN или policy routing.
- `eval "$choice"` в локальном root-меню позволяет выполнять произвольную команду, однако ввод уже контролирует оператор с root-доступом, поэтому самостоятельной удалённой границы повышения привилегий здесь не выявлено.
- В репозитории отсутствуют CI-тесты, Dependabot, `SECURITY.md` и опубликованные security advisories. Это не уязвимость само по себе, но снижает уверенность в процессе сопровождения.

## 6. Срочные действия для уже установленного сервера

1. Закрыть `9091/tcp` и `8080/tcp` на уровне cloud firewall/security group.
2. Не полагаться только на UFW: проверить Docker port publishing и цепочку `DOCKER-USER`.
3. Перевести Telemt API на loopback, включить аутентификацию и read-only.
4. Сменить все proxy secrets, пользователей, пароль панели и JWT.
5. Удалить Watchtower и запретить автоматические обновления неприкреплённых образов.
6. Проверить `iptables-save`, `nft list ruleset` и публичный IPv6.
7. Восстановить SSH allowlist и убедиться, что глобальный `ACCEPT` удалён только после проверки резервного канала доступа.
8. Проверить наличие `mtpr-zapret2.service`, Telemt, MTG и оставшихся helper/watcher-служб.
9. Настроить `StrictHostKeyChecking=yes` и проверить fingerprints удалённых нод.
10. На хосте с ценными данными рассмотреть переустановку ОС из доверенного образа: после выполнения неприкреплённого интернет-кода ручная очистка не доказывает восстановление доверия.

## 7. Рекомендуемый безопасный baseline

- отдельный минимальный VPS без других сервисов и пользовательских данных;
- SSH только по ключам и только из административной CIDR/VPN;
- все API и панели доступны лишь через loopback, VPN или mTLS/HTTPS reverse proxy;
- proxy engine запускается от отдельного непривилегированного пользователя;
- конфиги с секретами имеют режим `0600` или `0640`;
- systemd hardening: `NoNewPrivileges`, `ProtectSystem`, `ProtectHome`, `PrivateTmp`, `CapabilityBoundingSet`;
- зависимости закреплены на SHA/digest и проверяются до исполнения;
- отсутствуют автоматические root-обновления;
- firewall имеет тесты для IPv4, IPv6, нескольких портов, рестартов и удаления;
- изменения `/etc` сопровождаются резервной копией и полноценным rollback.

## 9. Заключение

Текущий снимок проекта не демонстрирует явного злонамеренного поведения, однако безопасным по умолчанию не является. Даже после исправления локальных ошибок ключевой архитектурной проблемой останется выполнение изменяемого внешнего кода от `root` без независимой проверки происхождения.

До устранения находок SA-01—SA-06 и фиксации всей цепочки поставок проект следует использовать только в изолированной тестовой среде.
